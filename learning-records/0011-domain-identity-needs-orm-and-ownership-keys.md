# Domain identity needs ORM and ownership keys

A feature specification can describe the facts a table represents without spelling out every key the
persistence layer needs. Translating the domain model into SQLAlchemy requires identifying three
related but distinct things: the row identity the ORM can track, the uniqueness rules the database
must enforce, and the ownership data PostgreSQL needs to isolate personal rows.

## Historical context

This insight surfaced while implementing issue
[#218](https://github.com/samanthablasbalg/rainbowsamreads/issues/218) on 2026-10-27, against
repository baseline
[`1435e43`](https://github.com/samanthablasbalg/rainbowsamreads/commit/1435e43bf7c400ea4221a3dff1f5b52a0cf3de2b).
The issue specified an `id` for `Recommender`, but described `BookRecommendation` only through its
fields and the uniqueness rule `(user_id, book_id, recommender_id)`. The first autogenerated
migration was empty, which initially made the missing relationship `id` look like an omission in the
issue.

There were actually two separate boundaries involved. Alembic compares the database with the
`MetaData` supplied by the application; it does not discover model files by scanning the models
directory. The new module therefore had to be imported so that its declarative class definitions
could register their tables with `Base.metadata`. Adding names to a package's `__all__` was not
enough, because `__all__` controls what an already-populated module exports during a wildcard
import; it does not import or bind those names.

Once the module was imported directly, SQLAlchemy exposed the next requirement: every ORM-mapped
class needs a primary-key identity. A `UNIQUE` constraint can prove that a combination of database
values does not repeat, but SQLAlchemy does not infer its identity map from arbitrary unique
constraints. In this case no surrogate `BookRecommendation.id` was needed. The issue's natural
identity was already the three-column combination `(user_id, book_id, recommender_id)`, so marking
those columns as a composite primary key both gives SQLAlchemy a stable row identity and enforces
the stated uniqueness rule. The primary key already implies uniqueness; adding the same
`UniqueConstraint` would duplicate it.

## Ownership is local as well as relational

`Recommender.user_id` and `BookRecommendation.user_id` carry the same value but protect different
personal facts:

- `Recommender.user_id` identifies whose private recommender identity the row represents.
- `BookRecommendation.user_id` identifies whose private relationship with the shared book the row
  represents.

The second column is logically derivable by joining through the recommender, but it is stored
locally on purpose. ADR-0023 applies the project's standard RLS policy directly to every personal
table's ownership column, allowing PostgreSQL to decide whether each recommendation row is visible
or writable without making ownership depend on a join.

The repeated owner also enables a composite foreign key from
`BookRecommendation(recommender_id, user_id)` to `Recommender(id, user_id)`. A foreign key on
`recommender_id` alone would prove that the recommender exists, but would not prove that the
recommendation and recommender belong to the same user. The composite foreign key makes that
cross-user link structurally impossible. PostgreSQL requires the referenced `(id, user_id)` pair to
be unique, so `Recommender` needs that unique constraint even though `id` remains its ordinary
primary key. Its separate `(user_id, name)` constraint enforces a different domain rule: exact
recommender names are unique within one user's private list.

## Evidence

The user recognized that the existing `BookAuthor` association model did not need a separate unique
constraint in addition to its composite primary key. That observation separated database uniqueness
from the mistaken assumption that every mapped table needs a new surrogate `id`, and led to the
follow-up question about why ownership appears on both sides of a personal relationship. Tracing RLS
and the ownership-enforcing composite foreign key connected the repeated column to a concrete
security invariant rather than treating it as accidental duplication.

## Implications

- When Alembic omits a new table, first verify that importing the application model package places
  the table in the exact `MetaData` passed to Alembic.
- When a specification does not name a surrogate `id`, look for the domain's natural candidate key
  before inventing one.
- A primary key supplies uniqueness as well as ORM identity; do not repeat the same rule with a
  `UniqueConstraint`.
- Treat a local `user_id`, an RLS policy, and an ownership-enforcing composite foreign key as
  complementary guarantees: row visibility and valid cross-table relationships are separate
  concerns.
