Request fields are not database fields

A practical guide to separating an API command from the domain state it coordinates.

Key idea: a request schema says what an operation needs as input. It does not say which object owns that information or whether the information is stored at all.

The Reading Tracker example

audio_length_minutes appears on the engagement-creation request. That makes it look like an engagement property, but tracing the operation shows otherwise. 

EngagementCreate.audio_length_minutes
        ↓
engagement lifecycle service
        ↓
capture_audio_length(book, edition, length)
        ↓
Book.default_audio_minutes + Edition.audio_minutes

No audio_length_minutes column is stored on Engagement. The create-engagement command carries a newly learned edition fact because starting the read and capturing that fact need to succeed or fail together.

Three shapes that answer different questions

Shape Question it answers Example
Request schema What must the client provide for this operation? EngagementCreate
Service command Which domain changes must happen in one transaction? Create a binding and capture a missing edition length
Persistence model Which entity owns durable state? Edition.audio_minutes

Ownership versus coordination

ADR-0021 assigns real format and length to Edition. It assigns a personal correction to EngagementEdition.length_override. An API operation may touch both without moving either fact onto Engagement. 

Edition.length                 shared edition fact
Book.default_*                 shared format fallback
EngagementEdition.override    this read differs
EngagementCreate field        command input, not ownership

This is useful when one user action spans several entities. Sending two separate requests could update the edition successfully and then fail to create the engagement. One command lets the backend apply both changes in one database transaction.

How to determine whether a field is stored

  1. Find the request schema to establish where the value enters.
  2. Trace the API handler into the service instead of inferring ownership from the URL.
  3. Follow assignments and constructor arguments to see which domain objects change.
  4. Check ORM models and migrations for the actual persisted columns.
  5. Read tests for observable behavior, while remembering that tests can encode accidents.
  6. Compare the result with the relevant ADR, which records intended ownership.
