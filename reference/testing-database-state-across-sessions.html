Testing database state across sessions

Decide between commit(), expire_all(), and refresh() by asking who wrote the state and who needs to see it.

Key idea: the test's db fixture and a TestClient request use separate SQLAlchemy sessions. Sharing a database does not give them a shared in-memory view.

The three phases

Phase Who writes? What the test session does
Arrange The test directly mutates an ORM object commit() so the API session can see the setup
Act The API request changes state Nothing; the endpoint owns its transaction
Assert The test reads what the API persisted expire_all(), refresh(), or query again

Arrange: publish test-authored state

book_obj.default_audio_minutes = 600
db.commit()  # make setup visible to the API's connection

response = client.post(...)

An uncommitted ORM mutation belongs only to the transaction that made it. The commit is correct here because the test—not the endpoint—authored the change.

Act: let the endpoint own its transaction

response = client.post(...)

# Do not call db.commit() to commit the API's work.
# db is a different session.

Calling db.commit() after the request commits the test session. SQLAlchemy normally expires that session's objects on commit, so later access may reload them, but using commit for that side effect hides the test's actual intent.

Assert: discard stale in-memory state

db.expire_all()
book_obj = db.get(Book, book_id)
edition_obj = db.get(Edition, edition_id)

assert book_obj.default_page_count == 250
assert edition_obj.page_count == 250

expire_all() marks everything currently loaded by the test session as stale; the next attribute read reloads it. Use refresh(object) when only one object needs an immediate reload.

A response dictionary is not an ORM object

book = response.json()  # snapshot at response time

client.post(...)        # later database change

# book still contains the old serialized values

JSON has no identity map, database connection, or automatic refresh. Make another API request or reload through a session to observe later state.

Decision checklist

  1. Which session made the change?
  2. Is this arrange, act, or assert?
  3. Does another connection need to see test-authored setup? Commit it.
  4. Did the endpoint author the change? Let the endpoint commit it.
  5. Could the test session have cached the object? Expire, refresh, or query again.
  6. Is the value only in an old JSON response? Fetch a new representation.
