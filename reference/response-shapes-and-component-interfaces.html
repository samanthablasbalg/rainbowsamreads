Response shapes and component interfaces

Return what an HTTP operation needs, then let each frontend module depend on only the structure its behavior requires.

Key idea: one domain entity may have several legitimate response shapes. TypeScript allows a richer value to satisfy a smaller component interface when it contains every required field.

Two interfaces, two questions

Interface Question it answers Owner
HTTP response model What does this operation promise to return? Backend operation
React prop type What may this module require from every caller? Frontend module

A smaller response can reduce database loading and the public contract. A smaller prop type limits module dependencies, but it does not remove fields from an object already in memory.

Derive a response from the operation

  1. Identify the caller and the behavior this operation supports.
  2. Trace every field the caller consumes, including downstream dialogs and forms.
  3. Separate implementation inputs from response outputs.
  4. Exclude data the caller already receives elsewhere.
  5. Check which ORM relationships and computed properties serialization would require.
  6. Keep fuller response models for operations that genuinely need the fuller entity.

Sorting by updated_at, joining through a relationship, or checking ownership can be necessary to implement an operation without making those values part of its response.

Issue #263: one entity, two projections

The book page needs complete engagement history. The catalog needs one selected engagement only to display and change status. Its target contract is therefore smaller: 

class CatalogEngagementRead(BaseModel):
    id: UUID
    status: ReadingStatus
    formats: list[Format]
    cover_url: str | None

class CatalogBookRead(BookRead):
    engagement: CatalogEngagementRead | None
Field Why it crosses the catalog interface
id Update the existing engagement.
status Render the label and choose between update and create behavior.
formats Choose pages or minutes when finishing a mixed-format engagement.
cover_url Preserve the engagement-specific cover in the finish sheet.

The full EngagementRead remains appropriate for engagement-history operations. The smaller catalog projection does not replace it.

Structural compatibility on the frontend

TypeScript compares the required fields, not the declared names of the source and target types. The shared dropdown can declare one smaller interface: 

type StatusDropdownProps = {
  book: BookRead;
  engagement: CatalogEngagementRead | null;
};
Value supplied Accepted? Reason
CatalogEngagementRead Yes It has exactly the required fields.
EngagementRead Yes It has every required field plus additional ones.
CatalogEngagementRead passed to a progress form No It lacks the progress fields required by EngagementRead. 
// Full history supplies EngagementRead | null.
<StatusDropdown book={book} engagement={selectedEngagement} />

// Catalog supplies CatalogEngagementRead | null.
<StatusDropdown book={book} engagement={book.engagement} />

No conversion, field stripping, extra request, or union type is required. Both callers pass an existing object reference. The dropdown may rely only on the fields declared by its prop type.

Follow the shared workflow downstream

Anything opened by a shared module must work with the data that module can receive. FinishReadSheet therefore needs the smaller engagement plus the separately available book. It cannot continue requiring fields absent from the catalog response.

StartReadingSheet does not need the same change. It already receives a book and an optional engagement id rather than a full engagement. Narrow only the interfaces affected by the actual response change.

When a smaller shape earns its keep

Use a smaller shape when Keep the full shape when
The full response forces otherwise unnecessary queries or relationships. The operation genuinely presents the complete entity.
Several callers have different representations of the same concept. Every caller naturally already has and uses most of the full response.
A shared module needs a stable subset from every caller. The proposed type is speculative and has no second source or concrete pressure.
Unrelated future fields should not silently enlarge this contract. Narrowing would add names without reducing caller knowledge or backend work.

Final check

  1. Can every returned field be tied to caller behavior?
  2. Have downstream sheets and forms been included in that trace?
  3. Are selection and authorization fields omitted when the caller does not use them?
  4. Does the response avoid nesting data already provided beside it?
  5. Can each shared module be satisfied by every one of its callers?
  6. Will the compiler reject the smaller value at modules that require the full entity?
