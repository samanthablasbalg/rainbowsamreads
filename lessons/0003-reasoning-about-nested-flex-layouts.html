Build the box relationships before choosing classes

The goal is not to memorize a class string for one header. It is to look at any design, identify which things must move together, and give each relationship the correct layout owner.

A layout utility changes one relationship

Every element participates in two relationships. Its outer display controls how the element sits beside its siblings. Its inner display controls how its children are laid out.

flex

The element is block-level among its siblings. Inside it, its direct children become flex items.

inline-flex

The element flows inline among its siblings. Inside it, its direct children still become flex items.

The difference is outside the container, not inside it. This is why both can put an icon and a label in a row, while inline-flex is often convenient when the whole group should behave like a phrase or badge.

Flex sees one level of the tree

Consider a toolbar with this element tree:

toolbar
├── title
└── account-group
    ├── name
    └── avatar

If toolbar is a flex container, its flex items are title and account-group. The name and avatar are descendants, but they are not direct children of the toolbar. The toolbar cannot set the spacing between them.

If the name and avatar need their own row, account-group must become a second flex container. One element can be a flex item in its parent and a flex container for its own children at the same time.

If both containers use flex, how many relationships are being controlled?

Main axis and cross axis answer different questions

A default flex row has a horizontal main axis and a vertical cross axis. Tailwind keeps those two questions in different utility families:

justify-*

Positions the flex items along the main axis. In a row, this means left/right and how horizontal free space is distributed.

items-*

Aligns flex items along the cross axis. In a row, this means their vertical relationship.

What justify-between actually distributes

Space is inserted between every pair of direct children. With three children, you get three visual anchors. If B and C should remain a tight unit, changing the gap or alignment cannot express that. The element tree must first say that B and C are a group.

These are design choices, not stronger and weaker versions of the same utility. A row dominated by typography may want baseline alignment. A compact icon-and-label group often wants center alignment. Nested containers allow both decisions in one component.

Spacing belongs to the parent-child relationship

A flex container's gap inserts gutters only between its direct children. It does not add space before the first child or after the last one. That makes a gap express “these siblings belong together, with this much separation” more directly than giving individual children left and right margins.

Nested groups can—and usually should—have different gaps. A toolbar may use a generous gap between major controls while an icon-label pair uses a much smaller one. There is no single gap that can describe both relationships.

Keeping a row together is a sizing problem

Flex rows do not wrap their flex items by default, but flex items are allowed to shrink. Text inside a shrinking item can still wrap at spaces. These utilities answer different questions:

Utility What it changes Diagnostic question
shrink-0 The flex item refuses to become narrower than its base size. Must this entire group preserve its width while a sibling yields space?
whitespace-nowrap Text inside the element cannot break at normal whitespace. Is the group intact, but a phrase inside it breaks onto two lines?
flex-wrap Flex items may move onto additional flex lines. Should whole sibling items deliberately flow onto another row?
min-w-0 A flex item may shrink below its content's automatic minimum width. Should long content truncate or wrap instead of forcing the row wider?
Do not add all four defensively. First create the right grouping, resize the page, and identify the actual failure: item wrapping, text wrapping, refusal to shrink, or overflow.
