Specializing a generic CRUD query

The catalog is not asking for a more powerful generic list(). It is asking for a different result: one book plus one optional, deliberately selected engagement. Recognizing that difference makes the Python design much easier.

Start with the promise already made

CRUDBase[Book].list() currently makes a strong, useful promise: “return a list of this model type.” Its type is conceptually list[Book]. Loader options may change which relationships are already loaded, but they do not change that result type.

The catalog needs a different cardinality and shape: list[(Book, Engagement | None)], or an equivalent named projection. It must also choose one engagement when several exist. That is why overriding the existing list() with a different return type would be misleading even if Python let it run.

Design rule: preserve the inherited generic method and give the specialized result a specialized name and return type.

Three Python designs

Design What it says Use it when Main cost
Specialized subclass A book repository has extra persistence queries. The project deliberately keeps model-specific SQL in CRUD objects. Another class and export; it should not import HTTP response schemas.
Module-level service/query function This operation has a use-case-specific query. The query exists for one workflow and Python module functions already express nearby workflows. The function needs an honest result type rather than hiding behind Book.
Mutate the singleton instance This one object gains behavior at runtime. Almost only tests, plugins, or temporary experiments. Poor discoverability and static typing; method binding is easy to get wrong.

Option A: subclass without overriding

class BookCRUD(CRUDBase[Book]):
    def list_catalog_rows(...) -> list[CatalogRow]:
        ...

book_crud = BookCRUD(Book)

This is ordinary inheritance: the instance keeps get(), create(), and the original list(), while gaining a book-specific method. Python's inheritance rules make this the conventional class-based extension point.

The new method should return a persistence-layer value such as a typed tuple or small dataclass. Returning CatalogBookRead from CRUD would make the lowest layer know about the API contract and reverse the repository's existing dependency direction.

Option B: a module-level function

@dataclass(frozen=True, slots=True)
class CatalogRow:
    book: Book
    engagement: Engagement | None

def list_catalog_rows(db: Session, ...) -> list[CatalogRow]:
    ...

Python does not require a class merely to namespace one query. A function is often the clearest choice when there is no mutable repository state and no family of interchangeable repository implementations. In this repository, the book service already contains specialized selection queries, so this option matches the local shape well.

The dataclass is optional. A tuple is smaller, but names make the boundary clear and keep the route's conversion code readable. The important part is that the type admits None for books without an engagement.

Option C: attach a method to one object

book_crud.list_catalog_rows = MethodType(list_catalog_rows, book_crud)

Python can do this, but a function stored on an instance is not automatically bound the way a function stored on a class is. Manual binding uses types.MethodType; the descriptor guide explains why. The language tutorial itself warns that even assigning external functions onto classes can confuse readers. On one singleton, type checkers also cannot see the method from its declared type, and importing a module can silently become the action that installs behavior. This is dynamic Python, but not the maintainable default here.

Why changing CRUDBase is probably the wrong generalization

A generic hook is earned when several model repositories need the same variation. Adding “optional joins,” “selected related rows,” or arbitrary statements to the base now would make its type contract less precise for one caller. A generic execute(statement) wrapper also adds little: Session.execute() already is that abstraction.

If a second and third model later need the same stable query protocol, that evidence may justify a hook or another generic result type. Until then, a specialized name localizes the complexity.

The SQL problem hiding inside “left join”

A plain left join preserves books with no engagements, but it produces one result row per matching engagement. Therefore a book with three historical engagements appears three times. The operation first needs a rule that ranks engagements within each book, then it can left-join only rank one.

  1. Rank candidate engagements inside each book partition according to the catalog rule.
  2. Expose that ranking as a subquery and alias it back to the engagement model.
  3. Left-join books to only the first ranked candidate.
  4. Keep the rank restriction in the join condition so a missing engagement remains None.

SQLAlchemy documents this as a row-limited window-function pattern. The same idea can remain local to one statement; it does not have to become a mapped relationship.

A left join solves “keep parents with no child.” It does not solve “choose exactly one child.” Those are separate requirements.

Result shape: do not throw the joined object away

SQLAlchemy distinguishes the FROM clause from the selected columns. Joining an engagement while selecting only Book still returns only books. Selecting both produces result rows containing both values. The ORM SELECT guide makes this distinction explicit. 

select(Book)              # result carries Book
select(Book, engagement)  # result carries Book and Engagement | None

This also explains a common trap: calling .scalars() on the second shape keeps only the first selected element. If the route needs both values, preserve and unpack the rows, then translate each pair into the response projection.

Loading is a separate axis

The selected engagement's formats and cover_url are computed from edition bindings and edition data; the book response also needs its authors. Selecting the right engagement does not automatically load those relationships. Loader options should be chosen for each selected entity to avoid accidental lazy loads or N+1 queries.

SQLAlchemy's relationship-loading guide stresses that a join used to determine rows and a joined/select-in loader used to populate relationships have different jobs. Keeping those jobs distinct makes the query easier to reason about.

Pydantic will read attributes; it will not invent them

With from_attributes=True, Pydantic can read matching attributes from ORM objects, including nested ones. But a Book has an engagements collection, not the catalog's singular selected engagement. Calling CatalogBookRead.model_validate(book) cannot infer the selection rule or rename that collection.

The boundary therefore needs either explicit construction from the two query values or an adapter object whose attributes already match the response shape. The Pydantic model documentation describes from_attributes as attribute lookup, not projection logic.

My judgment for this repository

Prefer the module-level book service/query function first. The operation is catalog-specific, combines selection with a projection, and nearby book-service functions already contain specialized SQL. Return a named persistence result and let the API layer construct CatalogBookRead and CatalogEngagementRead.

The specialized BookCRUD subclass is also respectable if you make a conscious repository-wide decision that model-specific persistence queries belong in CRUD classes. In that case, add a new method; do not change the meaning of list(). Avoid modifying the instantiated singleton at runtime.
